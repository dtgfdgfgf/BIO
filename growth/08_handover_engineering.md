# 08 交機工程：從「能跑」到「交得出去」

> **Summary (EN)**: Handover changes the audience from me to a shop floor where I am not present. The inherited program "worked", but the build on the machine could not be traced to any commit, executables were rebuilt in place without backup, memory was held up by finalizers, logs grew without bound, a background exception could end the program, and some settings could make inspection silently pass everything. The agent's first handover audit was a list of nearly 60 items that I could not really review. I switched to a single graded checklist with my ruling on each item, one short proposal per step, and offline-verifiable work only while the machine was unavailable. The work itself: build info embedded from git, a backup-and-manifest deploy procedure, measured memory release plus a 30-plate stress test, bounded logs, fail-safe "not inspected" states instead of silent OKs, and a parallel code review whose findings I ruled on one by one.

---

## 背景

交機階段一開始，LLM 先做了一次「除演算法以外」的工業級交機審查。結論是**未達交機標準**：最嚴重的 A 級 11 項、B 級 34 項、C 級 12 項。

同一時間，機台暫時不能測試。我決定 PLC 相關的修改和演算法調整全部暫停，只做離線就能驗證的事。

交機的對象不再是我，而是**我不在場的現場**。標準因此變了：不只要能跑，還要出錯時看得出來、查得到原因、回得去上一版。

## 1. 當時怎麼做

- **「能跑就好」**：程式能啟動、能判定，就算完成。
- **原地建置**：在機台的執行目錄直接重新建置，沒有備份，也沒有部署清單。
- **版本靠記憶**：現場跑的是哪一版，要靠回想最後一次是什麼時候建置的。
- **待辦一次丟出**：審查結果整理成一份長清單給我拍板。

## 2. 出了什麼事

| 發生的事 | 根本原因 |
|---|---|
| 選單列上的版本號是寫死的，從接手那天起就沒變過；文件寫「未部署」時，機台其實已經在跑新版 | 現場執行檔對不到任何 commit |
| 有幾次原地建置直接蓋掉舊的執行檔，沒有備份 | 部署沒有固定程序 |
| 每張影像約 10 MB 沒有即時釋放，全靠系統事後回收；連跑幾十盤，記憶體忽高忽低 | 相機影格、多餘的影像副本、縮圖用完沒有釋放 |
| 相機 log 累積到 28 GB，單檔 5.4 GB；舊圖清理在背景丟出例外，程式就整個結束 | log 沒有上限；背景工作沒有攔例外 |
| 檢測項目全部不勾，整盤會顯示綠色 OK；清空某些門檻，那一項就永遠不會判 NG | 設定可以讓判定**靜默失效** |
| 相機回呼出錯時，例外被丟回相機驅動的執行緒，程式直接結束 | 錯誤處理把可以恢復的錯誤變成當機 |
| 審查清單一次列了將近 60 項，我回：「太多了，沒有細看。」 | 一次給太多，拍板只是名義上的 |

## 3. 學到什麼

1. **交機的標準是「我不在場時，出錯看得出來、查得到、回得去」。** 能跑只是起點。
2. **寧可「未檢」，不可靜默放行。** 任何讓檢查失效的設定，都要在畫面上看得出來；NG 不可以被悄悄放過。
3. **版本可追溯是一切的前提。** 不知道現場跑的是哪一版，任何問題回報都對不上程式碼。
4. **驗證要對準真正的風險。** 釋放記憶體最大的風險不是「沒釋放」，而是「太早釋放」。這是我追問「釋放後會不會還要讀？」之後，LLM 才去補的壓力測試。
5. **交機清單要小到我消化得了。** 每輪只提一步，我同意才做。
6. **驗證不了的就先不做，但要記下來。** 機台不能測的期間，PLC 和演算法的修改全部暫停，缺口寫進清單，不假裝完成。
7. **多代理在這裡用對了地方。** [04](04_two_images_vs_2m_tokens.md) 說過，多代理放大的是執行品質，不是方向。程式審查正好是方向已經確定、只需要覆蓋面的工作。

## 4. 現在怎麼做

### 單一交機清單＋逐項裁決

- 交機缺口只有一份清單，分 A／B／C 三級，每一項都有狀態欄。做完就更新狀態欄，不另開新清單。
- 每一項由我裁決：做、暫緩、或不處理。不處理的也要寫明理由。例如「張數不符」的處理方式，我裁決為「急停，畫面顯示『請重驗』」。
- 每輪 LLM 只提**下一步**：做什麼、改哪些檔、不改什麼、怎麼驗證，短到一個畫面以內。我回「同意」才開始，做完再提下一步。

### 版本可追溯

- 建置時自動把 git commit 編號寫進程式，顯示在選單列、視窗標題，以及每盤報表的抬頭。有沒 commit 的修改，就加一個星號。
- 只看會進執行檔的路徑。只 commit 文件，版本號不跳。
- 要上機的執行檔，一定在 commit 之後才建置。每次有重建，回覆結尾都列出執行檔的完整路徑和它內嵌的版本。

### 部署程序

- 建置一律輸出到暫存目錄，不直接蓋機台目錄。
- 部署三步：先確認程式沒在跑，再備份執行檔和配方，最後複製並寫一份部署清單。
- 現場配方不可以整檔覆蓋，因為現場用參數頁改過的值只存在機台那一份。
- 實際部署由我下指令。LLM 自己寫入機台目錄的動作會被權限機制擋下，要我明確下令才放行。

### 記憶體釋放＋壓力測試

- 先量再改：演算法本身每張的未釋放量是 0，問題全在外圍。
- 改完之後，每張影像留在記憶體裡的量從 10.14 MB 降到 0.04 MB，判定和存檔逐位相同。
- 審查時抓到一個真問題：畫面上的小圖和放大檢視窗共用同一張圖，太早釋放會讓檢視窗崩潰。所以加了一條：「別的視窗還在顯示，就不釋放」。
- 壓力測試：真的主程式，6 條檢測執行緒、6 條相機執行緒，再模擬使用者亂點檢視窗和放大鏡，連跑 30 盤。結果判定與基準 0 差異、存檔逐位相同、記憶體不再爬升。這支測試可以重跑，之後只要改到釋放或畫面相關的程式，就要再跑一次。

### Log 有上限

- 相機 log 依大小切檔，總量設上限；待機時只抽樣記錄。
- 舊圖和舊 log 的清理包上例外處理，失敗只記錄，不讓程式結束。

### Fail-safe：「未檢」灰格

- 旁路、檢測項目全不勾、判定開關關閉、門檻空白，都一律顯示**灰色「未檢」**，不算 OK 也不算 NG，不計入良率。
- 主畫面用紅字寫出哪些項目沒在檢查，以及原因。
- 長時間執行的迴圈攔住例外後繼續跑；PLC 連續沒有回應，就在畫面上顯示紅字警告。相機出錯時跳出錯誤視窗，不結束程式。

### 整體程式審查

- 機台程式的執行期主幹分成 6 個子系統，由多個代理並行做唯讀審查。結果：高風險 4 條、中 20 條、低 26 條。
- 4 條高風險由我逐條裁決：2 條修、1 條不改、1 條因為現場 167 盤實際發生 0 次，先暫緩、併入另一項。
- 修了的那 2 條，就是上面「靜默失效」和「相機錯誤讓程式結束」兩件事。

## 後來

- 交機後開發移到公司電腦，兩層 git 合併成一個，版本追溯也跟著調整。
- 之後加的每個功能，例如「開始檢測前必須先復歸」「結束前確認已收筆」「燈獨立於開始／結束檢測」，都照同一套程序來：一步一提案、離線測試、commit 後建置、報告執行檔位置與版本。

## 限制

- PLC 斷線目前仍只告警、不自動重連，這是我當時的裁決；8 小時的實機長跑還沒做，因為機台當時不能測。
- 壓力測試沒有涵蓋檔案對話框，也沒有涵蓋真實機台的時序。
- 交機時有幾個修改已經 commit 但還沒部署，現場版本以程式顯示的版本號為準。
